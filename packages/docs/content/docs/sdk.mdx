title: SDK
description: "@driftwatch/sdk — add self-observing telemetry, drift detection, guardrails, and the full Autopilot loop to your own AI SDK agent."
---

`@driftwatch/sdk` is a library you add to an
[AI SDK](https://ai-sdk.dev) agent to make the agent self-observing. The SDK
traces every model step and tool call, detects behavioral drift, and enforces
per-request guardrails.

The SDK bundles no AI provider SDKs. It reads no environment variables on its
own. You pass it a model client, tools, and typed config as parameters. You
choose the provider. You choose where the config comes from.

The reference [server](/docs/server) and [console](/docs/console) are built on
this SDK. Use them to try DriftWatch without writing code, or as a blueprint for
your own service.

## Get started

### 1. Install

Install the SDK, the AI SDK, and one provider package for your model.

```bash
npm install @driftwatch/sdk ai zod
npm install @ai-sdk/openai   # or @ai-sdk/anthropic, @ai-sdk/google, …
```

### 2. Configure

Every SDK function takes typed config. You build that config in one of two ways.

**Option A — set environment variables** and let `loadDriftWatchConfigFromEnv()`
read them:

```bash title=".env"
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
PROMETHEUS_URL=http://localhost:9090
AGENT_MAX_STEPS=8

# Read by your provider package (@ai-sdk/openai), not by the SDK itself.
OPENAI_API_KEY=sk-...
```

```ts
import { loadDriftWatchConfigFromEnv } from '@driftwatch/sdk';

const config = loadDriftWatchConfigFromEnv(); // reads process.env
```

Start the process with `node --env-file=.env` so those values are in
`process.env` before anything reads them. (Node 20.6+ — no `dotenv` needed.)

**Option B — build the config object yourself** and validate it against the same
schema:

```ts
import { DriftWatchConfigSchema } from '@driftwatch/sdk';

const config = DriftWatchConfigSchema.parse({
  telemetry: { serviceName: 'my-agent' },
  agent: { maxSteps: 8 },
  driftDetection: { prometheusBaseUrl: 'http://localhost:9090' },
});
```

<Callout type="warn" title="Load your .env before you read it">
  `loadDriftWatchConfigFromEnv()` reads `process.env`. If you keep values in a
  `.env` file, start the process with `node --env-file=.env` (or your platform's
  own env injection). Otherwise the values are not in `process.env` yet, and you
  silently get the defaults.
</Callout>

Every field and its environment variable is listed in
[Configuration](/docs/configuration#sdk-config--driftwatchconfig).

### 3. Start telemetry

`bootstrapTelemetry` starts OpenTelemetry and sends traces, metrics, and logs to
any OTLP-compatible backend. The SDK ships it ready-made as a preload, so the
usual case needs no file of your own:

```bash
node --env-file=.env --import @driftwatch/sdk/preload app.js
```

That's the same call you'd otherwise hand-write, reading its config from the
environment. If you build a `DriftWatchConfig` in code instead, write your own
one-line module and `--import` that:

```ts title="telemetry.ts"
import { bootstrapTelemetry } from '@driftwatch/sdk';

bootstrapTelemetry({ serviceName: 'my-agent', otlpEndpoint: 'http://localhost:4318' });
```

<Callout title="Why a separate module, rather than a call at the top of your app?">
  ESM hoists every `import` above the body of the file that contains them, so
  `bootstrapTelemetry()` written "at the top" of your entry file still runs
  *after* every imported module has been evaluated. `--import` is the only way
  to run it genuinely first.

  How much that costs depends on what you use. DriftWatch's own signals are
  unaffected either way — `getTracer` returns a proxy that upgrades when the
  provider registers, and the metric instruments bind lazily for exactly this
  reason. `fetch`-based HTTP spans are unaffected too, since that
  instrumentation uses `diagnostics_channel` rather than import-time patching.
  What genuinely needs the preload is import-time-patched instrumentation:
  **pino, Fastify, and database drivers**.
</Callout>

With no `OTEL_EXPORTER_OTLP_ENDPOINT` set, this defaults to
`http://localhost:4318`. If nothing is listening there, the exporter logs a
connection failure and your agent keeps running — it never blocks on export. See
[Prometheus & OpenTelemetry](/docs/prometheus) to point this at a real backend.

### 4. Run an agent task

`runAgentTask` runs a traced tool-use loop. Give it a model and tools. It returns
the result and a usage summary, and — because `telemetry.ts` already started
OpenTelemetry — emits the `agent.run` trace and `agent.tool.*` metrics as it goes.

The example below is runnable. The tool calls GitHub's public API, which needs no
key; only the model needs a key.

```ts title="agent.ts"
import { runAgentTask, loadDriftWatchConfigFromEnv } from '@driftwatch/sdk';
import { openai } from '@ai-sdk/openai';
import { tool } from 'ai';
import { z } from 'zod';

const config = loadDriftWatchConfigFromEnv();

// A tool the agent can call. This one hits GitHub's public API — no key needed.
const tools = {
  get_repo: tool({
    description: 'Get public information about a GitHub repository',
    inputSchema: z.object({ owner: z.string(), repo: z.string() }),
    execute: async ({ owner, repo }) => {
      const res = await fetch(`https://api.github.com/repos/${owner}/${repo}`, {
        headers: { 'user-agent': 'driftwatch-demo' },
      });
      const data = await res.json();
      return { stars: data.stargazers_count, language: data.language };
    },
  }),
};

const result = await runAgentTask({
  prompt: 'How many stars does vercel/next.js have, and what language is it in?',
  modelClient: openai('gpt-4o-mini'), // any AI SDK provider; needs its API key
  tools,
  maxSteps: config.agent.maxSteps,
});

console.log(result.responseText);
console.log(result.skillsUsed, result.tokenUsage);
```

Run it with telemetry preloaded ahead of it. `--env-file` loads `.env`
(including `OPENAI_API_KEY`) before anything reads it, so this command is the
same on macOS, Linux, and Windows:

```bash
npx tsx --env-file=.env --import @driftwatch/sdk/preload ./agent.ts
```

You get the model's answer and the exact usage for that call:

```text
vercel/next.js has 129,304 stars and is written in JavaScript.
[ 'get_repo' ] { inputTokens: 812, outputTokens: 94, totalTokens: 906 }
```

`runAgentTask` returns the response text, the task id (searchable in your tracing
backend), which tools ran, the step count, and exact token usage — per call, with
no round trip to a backend. With telemetry flowing, the same call also lands in
your OTel backend as a trace within moments — see
[Verify it's flowing](/docs/prometheus#verify-its-flowing).

## Less wiring: `createAgentRuntime`

Everything above uses the SDK's primitives directly, which is the right level
when you want full control. Once an agent has its own guardrails and tool-call
policies, though, wiring each tool by hand means repeating the agent id on the
span and the gate, repeating the tool's name in two places that must match
exactly, and re-spreading a resolved config into the guardrails shape.

`createAgentRuntime` binds that context once. It's optional sugar — every
primitive below stays public and unchanged:

```ts
import { createAgentRuntime, DriftWatchConfigSchema, generateAgentSlug } from '@driftwatch/sdk';
import { tool } from 'ai';
import { z } from 'zod';

const runtime = createAgentRuntime({
  agent: {
    id: generateAgentSlug('Support Agent'),   // -> "support-agent-9e930e"
    name: 'Support Agent',
    guardrails: { maxTokensPerTask: 20_000 },
    toolPolicies: [
      { tool: 'issue_refund', field: 'amountUsd', condition: { gt: 100 },
        action: 'deny', severity: 'high', reason: 'refunds over $100 need a human' },
    ],
    createdAt: Date.now(),
  },
  config: DriftWatchConfigSchema.parse({}),
});

const tools = {
  issue_refund: tool({
    description: 'Issue a refund for an order',
    inputSchema: z.object({ orderId: z.string(), amountUsd: z.number() }),
    // One name, used for both the telemetry span and policy matching.
    execute: runtime.skill('issue_refund', async ({ orderId, amountUsd }) => ({
      refunded: true, orderId, amountUsd,
    })),
  }),
};

const result = await runtime.run({ prompt: 'Refund order A-4471 in full.', modelClient, tools });
```

`runtime.run()` resolves the agent's guardrails and `maxSteps` and attaches its
`agent_id` to every span and metric. `runtime.skill()` adds the telemetry span
and the policy gate. A deny-only policy needs no store and no notifiers at all.

<Callout title="Static agent, or live one?">
  `agent` takes either a definition or a function returning one:

  ```ts
  createAgentRuntime({ agent: myDefinition })                        // static
  createAgentRuntime({ agent: () => store.getAgentDefinition(id) })  // live
  ```

  A snapshot is right for an agent whose config is fixed at startup — no store,
  no per-run I/O. A function is re-resolved on every run, so a control-plane
  edit applies to the very next call. The choice is explicit at the call site
  rather than inferred, so an API that looks live can't silently be frozen.
</Callout>

## Instrument your own tools

Wrap a tool's `execute` in `withSkillExecutionSpan`. Every call then produces a
`tool.<name>` span and increments the `agent.tool.calls` and
`agent.tool.duration` metrics. These are the signals the drift detector reads.
Use this for any tool — a database lookup, an HTTP call, a vector search:

```ts
import { withSkillExecutionSpan } from '@driftwatch/sdk';
import { tool } from 'ai';
import { z } from 'zod';

const get_repo = tool({
  description: 'Get public information about a GitHub repository',
  inputSchema: z.object({ owner: z.string(), repo: z.string() }),
  execute: (input) =>
    withSkillExecutionSpan({
      skillName: 'get_repo',
      skillInput: input,
      executeSkill: async () => {
        const res = await fetch(
          `https://api.github.com/repos/${input.owner}/${input.repo}`,
          { headers: { 'user-agent': 'driftwatch-demo' } },
        );
        const data = await res.json();
        return { stars: data.stargazers_count, language: data.language };
      },
    }),
});
```

## Detect behavioral drift

`detectBehavioralDrift` queries two time windows through a `MetricsQuerySource`
you provide. It diffs the agent's behavior — tool mix, error rate, p95 latency,
token spend. It then asks your model to classify whether the agent drifted, and
returns a schema-typed verdict:

```ts
import { detectBehavioralDrift, PrometheusMetricsSource } from '@driftwatch/sdk';

const report = await detectBehavioralDrift({
  modelClient: openai('gpt-4o-mini'),
  metricsQuerySource: new PrometheusMetricsSource({
    baseUrl: config.driftDetection.prometheusBaseUrl,
    bearerToken: config.driftDetection.prometheusBearerToken || undefined,
  }),
});

console.log(report.verdict);
// {
//   drift: true,
//   severity: 'medium',
//   reasons: ['error rate 1% → 8%', 'p95 latency 210ms → 680ms'],
//   recommended_action: 'Investigate the rising error rate before it spreads.'
// }
```

`PrometheusMetricsSource` is the SDK's built-in `MetricsQuerySource` — it
queries any Prometheus-compatible `/api/v1/query` API (Prometheus itself,
Grafana Mimir/Cortex/Thanos, ...). Targeting a different metrics backend
instead? Implement `MetricsQuerySource` yourself and pass that.

Pass `isDryRun: true` to skip the metrics source entirely and use built-in
fixtures — a baseline window and a shifted "current" window. This lets you
test the verdict path before any real traffic exists, which is useful for
demos and CI. (`metricsQuerySource` is required unless `isDryRun` is `true`.)

The judge drives the model with `generateText` and parses its JSON defensively.
It retries up to 3 times (reported as `report.judgeAttempts`), so it works even
with providers whose structured-output support is unreliable.

## Enforce inline guardrails

Pass `guardrails` to `runAgentTask` for a hard, per-request cap. Drift detection
is aggregate and after-the-fact. A guardrail is synchronous: it stops a single
runaway call mid-loop, before the call finishes.

```ts
const result = await runAgentTask({
  prompt,
  modelClient: openai('gpt-4o-mini'),
  tools,
  maxSteps: config.agent.maxSteps,
  guardrails: {
    maxTokensPerTask: 40_000,   // 0 disables this check
    maxCostUsd: 0.5,            // 0 disables; derived from the prices below
    pricePer1kInput: 0.005,
    pricePer1kOutput: 0.015,
    onExceed: 'stop',           // 'stop' halts mid-loop; 'flag' finishes and marks it
  },
});

if (result.guardrailTriggered) {
  console.warn('guardrail hit:', result.guardrailReason);
}
```

## Run the full Autopilot loop

Drift detection is the *perceive* step. The SDK also contains the *reason → act*
orchestration: `ApprovalService`, `AutopilotScheduler`, `executeControlAction`,
and the notify-dispatch helpers. Together they give you the whole
notify/approve/act loop, not just the detector. None of it does concrete I/O. It
runs on the `StateStore` and `Notifier` interfaces, which you supply.

```ts
import {
  MemoryStateStore,
  ApprovalService,
  AutopilotScheduler,
  PolicyConfigSchema,
  PrometheusMetricsSource,
  type NotifierRegistry,
} from '@driftwatch/sdk';

const store = new MemoryStateStore();             // or RedisStateStore, below
const notifiers: NotifierRegistry = { list: [] }; // add real channels, below

const approvalService = new ApprovalService({
  store,
  notifiers,
  approvalTimeoutMs: 600_000,
  timeoutDecision: 'rejected', // a missed approval fails closed
});

const scheduler = new AutopilotScheduler({
  store,
  notifiers,
  approvalService,
  modelClient: openai('gpt-4o-mini'),
  policyConfig: PolicyConfigSchema.parse({
    rules: [{ when: { severity: 'high' }, do: ['notify_slack', 'pause_agent'] }],
    mode: 'shadow', // start here — logs intended actions, executes nothing
  }),
  metricsQuerySource: new PrometheusMetricsSource({
    baseUrl: config.driftDetection.prometheusBaseUrl,
    bearerToken: config.driftDetection.prometheusBearerToken || undefined,
  }),
  isDryRun: false,
  scanIntervalMs: 60_000,
  cooldownMs: 300_000,
  logger: console,
});

scheduler.start();
```

**State store.** `MemoryStateStore` is the zero-dependency, single-process
default. For a multi-process deployment, use `RedisStateStore`. It lives at the
isolated subpath `@driftwatch/sdk/redis`, so importing the SDK's package root
never pulls in `ioredis`. Only code that imports this subpath needs it:

```ts
import { RedisStateStore } from '@driftwatch/sdk/redis';

const store = new RedisStateStore(process.env.REDIS_URL!);
```

**Notifiers.** The SDK defines the `Notifier` interface and the dispatch helpers
(`notifyAll`, `safeNotify`, `notifierForAction`). It contains no concrete channels.
Slack, Telegram, and generic-webhook notifiers live in the companion
[`@driftwatch/autopilot`](https://drift-watch-docs.vercel.app/docs/alerts-and-actions#channels)
package. You can also bring your own by implementing `Notifier`. See
[Alerts & Actions](/docs/alerts-and-actions) for the policy format and channel
setup.

## Export telemetry

`telemetry.ts` from [Get started](#3-start-telemetry) is the whole setup.
`bootstrapTelemetry` exports traces, metrics, and logs over OTLP/HTTP. Metrics
use **cumulative** temporality (the OTel default), which is what PromQL's
`increase()`/`rate()` — and so `PrometheusMetricsSource` — expect. Logs carry
`trace_id` and `span_id` for trace-to-log correlation. The
[Prometheus guide](/docs/prometheus#what-driftwatch-emits) lists every signal
it produces.

In production, the same preload works against your compiled output:

```bash
node --env-file=.env --import @driftwatch/sdk/preload ./dist/app.js
```

<Callout title="Import order, precisely">
  Prefer the preload. If you bootstrap from inside your normal import graph
  instead, DriftWatch's own spans and metrics still work (the tracer is a proxy
  that upgrades, and the metric instruments bind lazily), and so do `fetch`
  HTTP spans (`diagnostics_channel`-based). What you lose is import-time-patched
  instrumentation — **pino, Fastify, database drivers** — because ESM has
  already evaluated those modules before your first line of body code runs.
</Callout>
