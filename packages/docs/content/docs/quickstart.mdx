Get DriftWatch running and produce your first drift report. The fastest path is
Docker Compose — two containers, DriftWatch and Postgres, nothing else required.

<Callout title="Building the code instead?">
  Adding tools, changing the model wiring, running tests? Skip to [Running from
  source](#running-from-source).
</Callout>

## 1. Configure

Clone the repo (you build the image from it) and create your `.env` from the
template:

```bash
git clone https://github.com/codewithveek/drift-watch.git && cd drift-watch
cp packages/server/.env.example packages/server/.env
```

Open `packages/server/.env` and set three things:

- `QWEN_API_KEY` — your model key. The default deployment targets **Qwen Cloud**
  (an OpenAI-compatible endpoint). To use Anthropic, OpenAI, Google, or a local
  model instead, see [server.md → Model client](/docs/server#the-model-client).
- `DW_USER` / `DW_PASSWORD` — the administrator account, created on the **first**
  boot against an empty database. Public sign-up is disabled, so without these
  there is no way into the console. The password must be at least 12 characters,
  and you will be asked to change it on first sign-in.
- `DW_AUTH_SECRET` — signs session cookies. Generate one with
  `openssl rand -base64 32`. It must stay stable: changing it signs everyone out.

<Callout type="warn">
  There is no `AUTH_TOKEN`. Earlier versions had a single bearer token holding
  every permission over every agent, with no expiry and no revocation — it was
  removed rather than deprecated. Operators sign in; machines use scoped
  [API keys](/docs/security#api-keys) minted from the console.
</Callout>

To send telemetry now, also set `OTEL_EXPORTER_OTLP_ENDPOINT`,
`OTEL_EXPORTER_OTLP_HEADERS`, `PROMETHEUS_URL`, and `PROMETHEUS_BEARER_TOKEN` — the
[Prometheus guide](/docs/prometheus) walks through exactly where each value comes
from, including a one-command reference stack. You can skip this for now and
still try everything below via dry-run mode.

## 2. Run

From a clone of the repo (the build context is the repo root):

```bash
docker compose --env-file packages/server/.env up -d --build
```

That starts DriftWatch and Postgres. The server migrates its own schema at boot
and seeds the admin account, so there is no separate setup step. When it's up:

```bash
curl localhost:4300/health          # → {"ok":true}
```

Open [http://localhost:4300](http://localhost:4300) and sign in with the `DW_USER` / `DW_PASSWORD` you
set. The image bundles the operator console, served at the root.

<Callout>
  Postgres is what makes API keys, the audit log, drift history and run charts
  survive a restart. It also removes the need for Redis *and* Prometheus — see
  [deployment.md](/docs/deployment).
</Callout>

## 3. Drive traffic

Send the agent a task. Each `/run` call executes a tool-use loop and returns
exactly what happened — no tracing backend required to see the result.

First mint a key: in the console, **API keys → New key**, with the `agent:run`
scope. Then:

```bash
curl -XPOST localhost:4300/api/v1/run \
  -H "authorization: Bearer $DRIFTWATCH_API_KEY" \
  -H 'content-type: application/json' \
  -d '{"prompt":"weather in Lagos, then search docs for onboarding"}'
```

<Callout>
  Every DriftWatch API route lives under `/api/v1`. The console owns the root, so
  `/agents` is a console *page* while `/api/v1/agents` is the resource.
</Callout>

```json
{
  "output": "It's 24°C in Lagos. Found 3 onboarding docs.",
  "usage": {
    "taskId": "b3f1…e2",
    "stepCount": 3,
    "skillsUsed": ["get_weather", "search_docs"],
    "tokenUsage": { "inputTokens": 812, "outputTokens": 96, "totalTokens": 908 },
    "providerName": "openai.responses",
    "modelIdentifier": "qwen3.5-plus"
  }
}
```

**What you get:** the task's id, how many steps it took, which tools it called,
and the exact token spend — per request, in the response body. The same data is
also emitted as OpenTelemetry traces and metrics for the drift detector and for
your observability backend.

To generate enough signal for a meaningful drift report, send a batch. The seed
script deliberately shifts the tool-call mix partway through, so there's a real
change to detect:

```bash
# from a repo clone; BASE_URL defaults to localhost:4300
pnpm seed 40
```

Put a `DRIFTWATCH_API_KEY` in `packages/server/.env` — the
seed script reads it from there, so the command above still needs no
shell-specific env-var syntax.

## 4. Get a drift report

The drift detector queries two time windows (baseline vs. current), diffs the
agent's behavior, and asks the model to classify whether it has drifted enough
to warrant a human alert:

```bash
curl localhost:4300/api/v1/drift -H "authorization: Bearer $DRIFTWATCH_API_KEY"
```

```json
{
  "currentWindowStats": {
    "totalCalls": 28,
    "errorRate": 0,
    "toolMix": { "get_weather": 0.71, "search_docs": 0.29 },
    "p95LatencyMs": 210,
    "tokenSpend": 26903
  },
  "verdict": {
    "drift": true,
    "severity": "medium",
    "reasons": ["search_docs share 40% → 75%", "token spend 12k → 27k"],
    "recommended_action": "Investigate the search_docs regression."
  }
}
```

<Callout type="info" title="No metrics backend yet?">
  Use the built-in fixtures — a baseline and a shifted "current" window — to
  see the full detection + verdict path with zero infrastructure:

  ```bash
  curl 'localhost:4300/api/v1/drift' -H "authorization: Bearer $DRIFTWATCH_API_KEY"   # with DRIFT_DRY_RUN=1 in .env
  ```
</Callout>

## 5. See it in your observability backend

Once telemetry is flowing, your OTel backend's service/trace views will show
`driftwatch` — request rate, latency, and errors — and let you inspect a single
task's full decision chain by `agent.task_id`. The
[Prometheus guide](/docs/prometheus) shows exactly what to look at (including
how to query Prometheus directly) and the queries that power drift detection.

## 6. Turn on alerts and autopilot (optional)

DriftWatch can act on drift — notify Slack/Telegram, or pause/rollback the agent
with a human approving from any channel. It's turned **off** by default and, when enabled,
starts in a safe shadow mode that logs intended actions without taking them.
See [alerts-and-actions.md](/docs/alerts-and-actions).

## Running from source

For contributors, or anyone customizing tools / the model client / policies.
Requires **Node ≥ 22** and **pnpm ≥ 9**.

```bash
git clone https://github.com/codewithveek/drift-watch.git driftwatch
cd driftwatch
pnpm install
cp packages/server/.env.example packages/server/.env   # then edit it
pnpm dev                                                # server + console, hot reload
```

- `pnpm dev` runs the server (`:4300`) and the console dev server (`:5173`)
  together; the console proxies API calls to the server.
- `pnpm --filter @driftwatch/server test` runs the test suite.
- `pnpm drift:dry-run` prints a fixture-backed drift report without a running
  server — handy in CI.
